# Changelog

## v0.3.0 — 2026-11-26

Upgrade notes: replace the Prometheus rules file (`deploy/prometheus/hwraid-exporter.rules.yml`: new `HwraidVolumesNotMonitored` description). New metric `hwraid_controller_qualified`; no series changes otherwise (checked on the reference host against v0.2.0). Two new commands are sent to the card at every cycle's opening, as the vendor tool does: `IsAdapterPaused` (704) every cycle, `CheckRevision` (701) once per card identity; an ordinary cycle on the reference host sends 64 commands instead of 63. A card of an unqualified model, unless allowed by `-allow-unqualified=aacraid`, no longer receives any command (before: the 706).

- aacraid: the size requested for the container list (229) is computed as the vendor tool does, 8 + 4 × `MaxContainers`, from `CT_GET_CONTAINER_COUNT` (public command, `docs/aacraid-interface.md`, section 4), read before the list and kept in memory like the 706 answer (read every cycle while the card identity is incomplete). The transport sends the list only at the size derived from the count validated for that card. `MaxContainers` outside 1 to 1023, or a list announcing more entries than `MaxContainers` (no chunk read beyond), makes the volume reads fail for the cycle. On the reference host, the requests are unchanged (256, so 1 032 bytes as before) apart from this one command, sent in the first cycle when the card identity is complete (every cycle otherwise): checked by a test that compares every request, byte for byte, over two cycles, with the sequence recorded before the change.
- aacraid: volume and disk reads are now two independent chains, in the same order as before. A failed count, container list, container information or member list no longer prevents the disk inventory and location (`disk_inventory`, `disk_location` collectors still read); a failed disk list (247) stops the member lists, disk information and connector map, and the volume and disk states. Before, any of these failures stopped all four collectors.
- aacraid: reads that depend on the card's capabilities, as the vendor tool decides (`docs/aacraid-interface.md`, section 7): without bit 9 of `FeatureBits`, containers and members are not read and the container count is not sent (`volumes` and `disks` unsupported, disk inventory still read); without bit 8, the connector map (708) is not read (`disk_location` unsupported, even when the disk reads fail); with bit 13 of `FeatureBits` or bit 15 of `SupportedOptions` (transfer forms not implemented), no volume or disk read is sent (collectors unsupported); a failed `RequestAdapterInfo` (703) stops the card's cycle (see the opening below), since the transfer format depends on it. The reference card announces bits 8 and 9 and neither bit 13 nor bit 15 (captured answers): no change there.

- aacraid: a paged transfer is abandoned without a close request after an error or a rejection during the transfer (failed ioctl, including `EINTR`; invalid or inconsistent chunk answer; data rejected before the close, such as a container list announcing more entries than `MaxContainers` or a transfer shorter than the decoded fields), as the vendor tool does on a wrong status or echo (its handling of the other errors is not established); before, the exporter sent a close request, never validated on hardware, which could target a transfer that does not exist or belongs to another tool. On the validated model and firmware, a stop requested during a transfer still sends the shortest committed sequence (chunk 0 if not yet sent, then the close if the chunks received are valid and their data accepted), with no data returned; other cards are described below. An open answer carrying the sentinel transfer identifier `0xffffffff` is refused with no further command, and the allowlist refuses that identifier in chunk and close requests. No change on the reference host's nominal sequence (checked byte for byte).
- aacraid: a model is qualified by its four PCI identifiers; the firmware is no longer a read condition. A card of a qualified model with a firmware other than the validated ones (`docs/aacraid-interface.md`, section 8, table of qualified models) is now read, with the vendor tool's command sequence: every chunk of each transfer then the close, the remaining chunks then the close when the service stops during a transfer, no re-read after a `0xc5` close; new commands after a stop are admitted for 2 s counted from the stop (the cycle deadline, or the moment the transport sees the stop signal), checked when each command is admitted, beyond which the transfer is abandoned without a close. Its cache protection is read once the 703 answer is valid, after the 803 attempt; a failed 703 publishes the `cache_protection` collector as failed. The vendor tool reads it on every card it has opened (opening checks below). The two differences from the vendor tool, reading only the needed chunks (accepted by the reference card's firmware) and one re-read after `0xc5` (a choice of the exporter), stay limited to the validated model and firmware (Adaptec 6805, 5.3-0[19204]). On that card, the cache protection requests now come after the 703 and the 803 instead of right after the 706, closer to the vendor tool; besides the count request above, this is the only change of its command sequence (checked byte for byte).
- aacraid: every open and chunk answer must carry `0xda` in word 4 and the total in word 7, the values the exporter's next request carries (the vendor tool copies these words from the previous answer into its next request); otherwise the transfer is abandoned. All the answers captured for the exporter's reads carry these values: no change on the reference host.
- aacraid: a card is opened as the vendor tool opens it: `IsAdapterPaused` (704) every cycle, then `CheckRevision` (701), the 703, and the 706 only if the 703 announces it (bit 16 of `SupportedOptions`, the Linux driver's condition too). A paused card, a refused revision or a firmware build below 2120 gets no further command in the cycle (`adapter paused`, `revision refused` in the log), as the vendor tool does not open it; so does a failure of any of these four commands. The 703 and 706 keep the form of the vendor tool's enumeration (`XferState` 1), in use since v0.1.0. Not reproduced yet: the rest of the vendor tool's opening after the 706 (further commands, which can still make it give up). Without the 706, the `capabilities` collector and the state reads are unsupported, the temperature and the cache protection are still read. The accepted 701 is kept like the 703. On the reference host, an ordinary cycle sends 64 commands instead of 63 (the 704), and the first cycle starts with 704, 701, 703, 706 (checked byte for byte against the vendor tool's captured requests).
- New option `-allow-unqualified=aacraid` (off by default, repeatable): cards of a model that is not qualified are read like the previous case. The commands are those of the vendor tool, checked against constructed answers only on such a model; risks in `docs/deploiement.md`. An unknown module name stops the startup; the `serial:<number>` form is not available yet. New metric `hwraid_controller_qualified` (1 if the model is qualified, 0 otherwise). A card of an unqualified model that is not allowed gets no firmware command at all (before: the 706), only the driver's `GET_HBA_INFO`; all its collectors are unsupported.
- Documentation: reading levels of a card and a side-by-side comparison of the vendor tool, the exporter on the validated pair and on other cards (order, chunks, stop, `0xc5`, errors, atypical opens, kept answers) in `docs/aacraid-interface.md`, section 8.

## v0.2.0 — 2026-11-25

Upgrade notes: replace the Prometheus rules file (`deploy/prometheus/hwraid-exporter.rules.yml`: new alert, new `HwraidDiskFailed` expression and texts). `hwraid_disk_state` gains the `vendor_state` label and new state values; `hwraid_volume_state` and `raid_level` gain new values (`docs/metrics.md`). No new command is sent to the card.

- aacraid: state of every present disk, members or not, following the vendor tool's rules on the disk information (248) and the card's capabilities (`docs/aacraid-interface.md`, section 6 bis): new normalized states `ready`, `spare` (global hot spare), `copyback`, `passthrough` (raw disk for the card: JBOD, native HBA), `unsupported`. New label `vendor_state` on `hwraid_disk_state` with the vendor tool's term (`Online`, `Hot Spare`, `Raw (Pass Through)`…), empty when the disk information could not be read; in that case only member disks get a state, from their member flags, as before. A present disk whose member partition is flagged failed now gets the disk's own state (for example `online`) instead of no state; the loss stays on the volume state. Dedicated spares are not read. Devices that are not disks (type other than 0, or removable, in the disk information; for example an enclosure) are no longer published as disks (no state, inventory, location or Linux device); a volume member on such a device is lost and the device is published `failed` (the vendor tool shows a missing failed disk instead), as is such a device flagged as a hot spare. When the disk information is incomplete or partly read, disks it declares failed are still published `failed`. More cautious than the vendor tool: a disk both declared failed and unsupported is published `failed` (the tool may show it `Unsupported`, out of any failure alert). A disk information answer without bytes 332-335 makes the cycle fall back to member-derived states. `HwraidVolumeFailed` description no longer asserts data loss for RAID 10 or 50 losses in different spans. `HwraidDiskFailed` aggregates without `vendor_state` (one alert per disk across the fallback) and its description covers the new cases.
- aacraid: volume state for every published level in the ARCIO numbering (the classic numbering stays `unknown`), following the vendor tool's tolerance rule (`docs/aacraid-interface.md`, section 6): lost members (failed, on a missing disk, on a disk its information declares failed, or rebuilding, except under the vendor tool's inhibition) compared with the level's tolerance (none, single, double). New states `reduced_redundancy` and `reduced_redundancy_rebuilding` (RAID 6 or 60 without one member, still tolerating a failure; an assembly inherits them from a member, without that guarantee for itself). Containers in a loop of assemblies are `unknown`, whatever the read order. Known limits: members on a partition the tool would not find, or on a disk of another block size, are not seen. Assemblies now get the most severe state of their member volumes (before: `unknown` as soon as a member was not optimal). More cautious than the vendor tool, by decision: outside the inhibition, a rebuilding member always counts as lost (the tool's result depends on member order); the rebuilding variant is kept only when no member is dead; an assembly takes its most severe member state (the tool merges in rank order, so a later member can mask a loss); an undetermined member, or an inconsistent assembly member, gives `unknown` unless the other members already call for action (`failed`, or `degraded`). `HwraidVolumeDegraded` summary no longer says "without rebuild" and its description covers a member of unknown state. Proof of loss (missing disk, or disk declared failed) wins over an unknown member flag. A member whose disk is missing is now lost even when flagged rebuilding.
- aacraid: the disk information (248) is read before the states are computed. If one of its reads fails, the answers already read in the cycle still count as proof of failure; disks not read are evaluated from their member flags. Its failed bit is read from any decoded answer.
- Alert rule `HwraidVolumeRedundancyReduced` (warning, 5 min) for `reduced_redundancy` and `reduced_redundancy_rebuilding`; `HwraidVolumeStateUnknown` and `HwraidDiskFailed` descriptions updated.
- aacraid: RAID level of the container types the vendor tool converts, following its conversion (`docs/aacraid-interface.md`, section 6 bis): two type numberings chosen per container, RAID 0, 1, 1E, 5, 5EE, 6, 10, 50, 60, Reed-Solomon variants, simple and spanned volumes, assemblies. New normalized `raid_level` value `single` (volume on one disk); 5EE and Reed-Solomon variants are published as `raid5`, `raid6`, `raid60`, the variant staying in `vendor_level`. Containers under migration, and types the vendor tool handles specially, stay `unknown` (more cautious than the vendor tool). The volume state follows the same classification as the published level (before, a raw type 3 in the classic numbering, a RAID 0, would have been evaluated as a mirror). A volume with a container member that does not make an assembly gets `unknown`, not `single` or `concat`. A disk information answer shorter than the status bytes keeps its inventory. A level is published only if the members match it (outside assemblies: only disks, at least the minimum of the vendor tool's creation table; assemblies: at least two members, one of them another container read in the cycle); otherwise `unknown`. Volume geometry (parity, multiples, maximums) is not revalidated: like the vendor tool, the exporter trusts the card for it. A member list with a rank not below the member count (an entry the vendor tool ignores) or a repeated rank (an exporter rule) is now refused (configuration read failed for the cycle: no volumes, disk states, disk inventory or location), as duplicates already were. No change on the reference host.
- aacraid: decoding of the fields the vendor tool uses for states (member rank, numbering selectors, task fields, disk status bytes, `FeatureBits`, native HBA option), from answers the exporter already reads: no new command.

## v0.1.3 — 2026-11-24

- aacraid: controller temperature published (`temperature` collector, qualified model and firmware only): `hwraid_controller_temperature_celsius` and the thresholds announced by the card, `hwraid_controller_temperature_threshold_celsius{level="low"|"high"}`. As the vendor tool does, `AdapterEnvironmentInfo` (803) is sent only if `RequestAdapterInfo` (703) announces a heat sensor (`AAC_SUPPORTED_HEAT_SENSOR`): a 703 answer without it makes the collector unsupported, a failed 703 a failed read, retried next cycle. The 703 answer is kept in memory like the 706 one (read every cycle while the card identity is incomplete); in steady state, one more command per cycle.
- Alert rules `HwraidControllerTemperatureHigh` (warning, 55 °C ≤ temperature < 60 °C for 10 min) and `HwraidControllerTemperatureCritical` (critical, ≥ 60 °C or at the card's high threshold, the vendor tool's abnormal state, for 5 min).
- `scripts/check-public.sh` also decodes hexadecimal strings of text files (responses recorded in Go tests, concatenated pieces joined) before looking for real values.

## v0.1.2 — 2026-11-24

Changes since v0.1.1. The `aacraid` driver loses one management command block, until the next reboot, each time a signal ends the wait of a program for the card before its answer arrives (`-ERESTARTSYS`; cards answered through `aac_intr_normal`, series 6 included, kernel 4.6 and later); once its pool of 8 is empty, no management tool can reach the card and the shutdown cache flush command cannot be sent. Most of this release protects against it: see `docs/aacraid-defaut-pilote.md`.

### Card commands and stop

- aacraid: controller commands are sent from a dedicated thread that blocks asynchronous signals (v0.1.1 could be interrupted by the Go runtime's own `SIGURG`). Only the fault signals stay unblocked; if the mask cannot be set, no command is sent.
- On `SIGTERM`, `SIGINT` or `SIGHUP`, the exporter starts no new cycle and no new collection, and sends no new command, `GET_HBA_INFO` included (the driver serves it under the same lock as management commands). The stop and the cycle deadline (compared with the clock) are checked on the ioctl thread right before each command; only the first chunk and the close of an open paged transfer are exempt, and such a read is not published. The command already sent is awaited with no limit of its own and a warning every 10 s: the supervisor's stop timeout is the only limit (`TimeoutStopSec=30s` in the systemd unit, `stop_grace_period: 30s` in the Compose examples). That bound is an availability trade-off: a command still running after 30 s is killed, losing a block and, for a command larger than a block, risking its DMA buffer (docs/aacraid-defaut-pilote.md).
- From the start of a stop, `/metrics` serves no hardware value (`hwraid_snapshot_ready 0`); a cycle interrupted by the stop is not published, and errors of collections still running are logged. `/metrics` also stops serving a view older than three intervals plus the collection timeout (stuck collection loop).
- `SIGPIPE` is ignored while serving: a log reader that goes away no longer kills the exporter during a card command.

### aacraid protocol

- A paged read whose close is acknowledged with `0xc5` is rejected, as the vendor tool does (it uses the data only for `CT_OK`), and retried once in the same cycle if its chunks were valid and the cycle is neither expired nor stopped; a second rejection is an error. v0.1.1 published the data of such a read.
- Every paged response must announce the size the card always uses (496 bytes, from 1 057 captured responses), and a transfer is engaged only if the open response carries `CT_OK` (`0xda`): a truncated or non-conforming open is followed by no chunk and no close, and a truncated close invalidates the read.
- A ZMM state word with status bits but without the installed bit no longer publishes `hwraid_cache_protection_present 1`: presence is omitted and the state published as `unknown`.
- When the capabilities read (706) fails, a card whose model and firmware are not qualified still publishes its unsupported collectors, and a qualified card publishes the reads it prevented as failed.

### Volume write cache

- New metrics `hwraid_volume_write_cache_policy` (configured setting: `write_back_always`, `write_back_when_protected`, `write_through`) and `hwraid_volume_write_cache_enabled` (current state), read from the volume information already collected, with no extra controller command.

### Per-card tracking

- The history kept per card (last success dates, `0xc5` counter, memory-served success, unsupported collectors) and the 706 and 708 answers kept in memory are tied to the card's hardware identity, one definition shared by the exporter and the module: serial number, PCI IDs, model, firmware (plus the address and device node). Any field read differently shows another card or firmware: the history is forgotten and the answers are read again. An unreadable field alone proves neither continuity nor replacement: nothing is forgotten, but nothing is kept in memory either (706 read every cycle), and memory-served successes and unsupported collectors are reused only after an effective collection under a complete identity.
- During a collection timeout or a failed node check, a collector served from memory (`capabilities`) stays successful if its last read succeeded on the same card, and collectors known as unsupported stay unsupported. While the node check fails, every other supported collector is published as failed (its prerequisite failed), with its last success date, and collectors known as unsupported stay published as such, so that losing all readings is reported even if those cycles alternate with timeouts, before or after a first success.
- `hwraid_transfer_close_unconfirmed_total` counts rejected reads, those of a collection finished after its timeout included: counted for the card of the cycle if returned within it, otherwise at the next collection of the same PCI address, and dropped if another card is observed there at that collection. Known limit: if the other card was observed at an earlier cycle, they are counted for it (a card swap requires a power cycle in practice, which restarts the exporter).

### Alert rules

- Rules use the published state only, never the last known value after a failed read; state, write cache, disappearance and intermittence alerts stay active for 10 minutes from the first rule evaluation without their condition (`keep_firing_for`, Prometheus 2.42 or later).
- Write cache: `HwraidVolumeWriteCacheUnprotected` (critical: cache active while protection is missing, failed or charging; to be checked in ARCCONF for every affected volume after changing the setting), `HwraidVolumeWriteCacheProtectionUnknown`, `HwraidVolumeWriteCacheUnknown`, `HwraidVolumeWriteCacheAlwaysOn`, `HwraidVolumeWriteCacheInactive`; every volume is evaluated, members of an array included.
- `HwraidVolumesNotMonitored` (warning, 1 h): a card recognised by a module whose volumes are not read (model and firmware not qualified, or state reads not announced by the capabilities answer).
- `HwraidCollectionIntermittent`: at least six success/failure transitions of a currently published collector in an hour, or four in four hours, which would otherwise keep `for` delays (up to 2 hours) from ever completing.
- `HwraidVolumeDisappeared` and `HwraidControllerDisappeared` raise one alert per object, even after a rename or a firmware update, and keep firing through a failed read. `HwraidCollectionStale` ignores a collector that has become unsupported. `HwraidCacheProtectionFailed`, `HwraidCollectionStale` and `HwraidCollectionNeverSucceeded` say what to do.

### Diagnostics and tools

- Every failed read of a published collection is logged, with the reads it prevented, errors of a collection finished after its timeout included. `ENOMEM` on a controller command is reported with its two possible causes: an exhausted driver pool, or a DMA buffer the driver could not allocate for a large command.
- `tools/aacraid-fib-trace.sh`, a kernel probe that names the programs losing command blocks. It writes to a new private directory (100 MiB by default), names its probe per run, drains the buffer before removing the probe and checks the removal, including on `SIGHUP`, `SIGINT`, `SIGTERM` or a closed standard output. Its summary says « trace complète » only if the capture started, nothing was missed or lost, the reader did not fail and the removal succeeded.

### Deployment and release

- The systemd unit is attached to each GitHub release and listed in `SHA256SUMS`; the documented check compares exact file names.
- Documentation: operating rules for the driver defect (stop with a 30 s grace period, never `docker kill` or `docker rm -f`, do not freeze the container, write cache with a failed protection module, exhausted pool, card replacement), per-card acceptance check.
- `scripts/check-public.sh` rejects email addresses outside `lore.kernel.org` links.

### Upgrade from v0.1.1

- The first stop is performed by the v0.1.1 process, which does not protect its commands: stop it once, with the 30 s grace period, and start v0.1.2 directly (docs/deploiement.md).

## v0.1.1 — 2026-11-23

- Apache License 2.0 (`LICENSE`, `NOTICE`, SPDX headers).
- Third-party licences shipped with the binaries: `/licenses` in the container image, licence archive next to the release binary.
- Security policy (`SECURITY.md`).
- aacraid: a paged-transfer close acknowledged with mark `0xc5` (seen when another tool such as maxView queries the card at the same time) no longer fails the collection; it is counted in `hwraid_transfer_close_unconfirmed_total`. v0.1.0 failed the volume and disk collectors on such a cycle.
- CI: `actions/checkout` 7.0.1 and `actions/setup-go` 7.1.0, pinned by commit.
- Docker seccomp profile (`deploy/docker/seccomp.json`): Docker's default profile without `iopl`/`ioperm`, which `SYS_RAWIO` otherwise allows.
- Collection stops sending controller commands once the cycle deadline has passed (a paged read in progress is still closed).
- Capabilities are kept only for modules with a card whose nodes were prepared.
- Discovery: unreadable or empty mandatory PCI attributes and an unreadable `driver` link are host errors instead of empty values.

## v0.1.0 — 2026-11-23

First release. `aacraid` module, qualified on Adaptec 6805, firmware 5.3-0[19204].

- Volume (mirrors, assemblies) and member disk states, normalized RAID level.
- Disk inventory (vendor, model, firmware, serial number, WWN, capacity), location (connector, position, phy) and link to the Linux device (`sgX`).
- Cache protection module (ZMM) state.
- Collection tracking: per-collector success, last success time, interval, per-card timeout.
- Example alert rules, tested with `promtool`.
- Docker image (`ghcr.io/disaster/hwraid_exporter`), static binary with its SHA-256 checksum, and systemd unit.
- Build information metric (`hwraid_exporter_build_info`: version, source revision, Go version).

Validated on hardware: optimal volume and disk states, inventory, location, Linux device, failed cache protection. Degraded, rebuilding and failed volume states and the charging and optimal cache protection states are tested on constructed data only.
